# Reliability Implementation Plan

For concrete modules, algorithms, persistence, HTTP behavior and acceptance fixtures, use [LOW_LEVEL_IMPLEMENTATION.md](LOW_LEVEL_IMPLEMENTATION.md). This file owns task status; a task is not complete solely because it appears in the specification.

Status values: `NOT_STARTED`, `IN_PROGRESS`, `BLOCKED`, `COMPLETE`.

A task is COMPLETE only when code, tests, failure handling, tenant isolation, observability, documentation, and acceptance criteria are satisfied.

## REL-04 Claim engine — STATUS: COMPLETE

- [x] Stable claim IDs. Explicit-claims mode: stable by construction (caller-assigned, uniqueness enforced). - [x] Preserve source offsets/references where practical. `Claim.start_char`/`end_char` are now populated by both extractors via a monotonic-cursor literal-substring search (`core.claims._locate_span`), correctly distinguishing repeated identical sentences/clauses from each other (`tests/test_claims.py::TestSimpleClaimExtractorOffsets`/`TestEnhancedClaimExtractorOffsets`). Left `None` only if a future extractor rewrites text instead of slicing it -- not reachable by either extractor today.
- [x] Unit and golden tests. Pre-existing `tests/test_verifier.py::TestGoldenCases` (supported/partial/contradiction/insufficient-evidence/mixed), `tests/test_dispatch_gates.py::TestExplicitClaimsMode` and the budget/injection fixtures below, plus new `tests/test_claims.py` (9 tests: offsets, extractor identity, ID determinism across an edit).

**Also closed this pass, pre-dispatch (ADR-012, shared by REL-04/REL-07):** `core/budgets.py`'s `MAX_CLAIMS_PER_REQUEST`/`MAX_EVIDENCE_PER_CLAIM`, checked once before any claim reaches a judge; exceeding either abstains `BUDGET_EXHAUSTED` with zero judge dispatch (`tests/test_dispatch_gates.py::TestVerifierBudgetGate`). ## REL-08 Scoring — STATUS: COMPLETE
- [x] Transparent score calculation. `core/scoring.py::ScoringEngine` implements scoring.md's exact v0.1 formulas; every `ScoreValue` carries `method_version` (e.g. `groundedness-0.1`) and `status` (`MEASURED|NOT_APPLICABLE|UNAVAILABLE`) -- matches `contracts/v0.1`'s `ScoreValue` schema (`status` always required; `value`/`method_version`/`calibration_class` required together only when `MEASURED`). Reconciled against this ledger for the first time this pass; the code itself predates it.
- [x] Groundedness, hallucination risk, contradiction risk. `_claim_ratio_score()`: count(predicate)/count(applicable claims), `NOT_APPLICABLE` at a zero denominator, no partial credit -- exactly scoring.md's formulas. `scope_breach`/`instruction_adherence`/`confidence_alignment` are always `UNAVAILABLE` (scoring.md: "no accepted v0.1 formula for them yet"); `citation_support`/`tool_correctness` are structural (deterministic, no judge). `determine_verdict()` implements scoring.md's precedence table exactly (any `CONTRADICTED` -> `FAIL`; all `SUPPORTED` -> `PASS`; all-insufficient/no-applicable -> `ABSTAIN`; else `PARTIAL`), independent of policy.
- [x] Explicit confidence/provenance. `ScoreValue.calibration_class`/`method_version` on every score; `derive_calibration_class()` is deterministic and changes with any input (evaluator/provider/model/config/qualification-status). `tests/test_scoring.py` (25 tests) covers the verdict-precedence table, ratio formulas at each denominator edge, and calibration-class determinism/sensitivity.
- [x] Calibration hook for future benchmark-driven scoring. `derive_calibration_class()` is exactly ADR-010's hook: an opaque, stable class today (no registry behind it yet), ready for G4 to attach real per-class agreement metrics to once qualification exists.

**Acceptance:** met. `contracts/v0.1`'s `ScoreValue` requirements (not scoring.md's aspirational extras) are the actual wire bar, and those are satisfied. Two known, non-blocking deviations from scoring.md's prose, stated rather than silently ignored: (1) scoring.md says "round only at presentation; preserve full internal precision," but `_claim_ratio_score()` rounds to 4 decimal places at computation time -- a pre-existing choice, not changed this pass, since revisiting it risks perturbing every golden-fixture value for a cosmetic-precision gain outside this task's scope. Neither is required by `contracts/v0.1`'s schema (`additionalProperties: true`; only `status`, and `value`/`method_version`/`calibration_class` when `MEASURED`, are required), so neither blocks wire compatibility or this task's completion.

**Post-review fixes (2026-09-16):** an independent review of this pass's own diff found three real gaps, all fixed and each confirmed by a test that fails against the pre-fix code and passes against the fix (not just added and assumed correct):
- Evidence IDs had no uniqueness validator (`Claim.claim_id` did, `Evidence.evidence_id` didn't) -- the API accepted two evidence entries sharing one ID, silently ambiguous for every downstream ID-indexed lookup. Fixed: `VerificationRequest.validate_unique_evidence_ids` (`schemas/verification.py`), mirroring the existing claim-ID check.
- A malformed `Content-Length` header (`int()` on a non-numeric value) crashed into an uncontracted plain-text 500 instead of the documented JSON error envelope. Fixed: `api/app.py::_enforce_content_length_limit` now catches the parse failure and raises a typed `INVALID_ARGUMENT` 400. (A real HTTP client's malformed header is separately rejected by uvicorn/h11 at the transport layer before reaching the app at all -- the bug was only reachable via an in-process ASGI caller, e.g. `TestClient`, which is presumably how it was found; the fix is still correct defense-in-depth at the layer this code owns.)
- The API accepted a JSON body sent with any `Content-Type` (e.g. `text/plain`), contradicting API.md's "JSON content type ... required." Fixed: `api/app.py::_require_json_content_type`, checked before the body is even read.
- Separately flagged (not a correctness bug, a scalability one): the route awaited `Verifier.verify()` directly, and a model-heavy provider's blocking call would freeze the whole event loop for every concurrent request on that worker. Fixed: dispatched through `starlette.concurrency.run_in_threadpool`. `tests/test_api.py::TestAsyncDispatchDoesNotBlockEventLoop` is a genuine regression test -- verified failing (health check delayed ~0.32s behind a 0.3s blocking call) before the fix and passing (~0.05s) after.
