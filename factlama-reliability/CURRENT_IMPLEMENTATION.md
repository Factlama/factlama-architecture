# Reliability implementation snapshot

Checked locally on 2026-09-13. `schemas/`, `core/`, `judges/`, `tests/`, and `examples/` exist in the implementation repository. Running `.venv/bin/python -m pytest -q` produces **136 passed, 1 skipped**. This establishes that the migrated-and-revised prototype behaves as its own tests expect; it does not satisfy the accepted [cross-repository contract](../CONTRACTS.md) or close a REL task.

A follow-up pass this same day closed the specific gaps recorded below on 2026-09-13 (wire shape, JudgeProvider port, provenance/calibration, scoring formula). What follows describes the resulting state, not the original migration.

`VerificationRequest` no longer carries `tenant_id`: tenant identity is a trusted argument to `Verifier.verify(request, tenant_id=...)`, never a client-payload field. `question` is optional; the evidence field is named `evidence` (not `context`); `project_id`/`application_id` are required; `interaction_id`/`trace_id`/`span_id`/`model`/`prompt_version`/`policy_id` are accepted and, for `trace_id`/`span_id`, echoed rather than always regenerated. `VerificationResult` now carries `evaluation_id`, `status` (`COMPLETED|ABSTAINED|FAILED`), `abstention_reason` (`NO_CHECKABLE_CLAIMS|INSUFFICIENT_EVIDENCE|PROVIDER_FAILURE|CANCELLED`), and a structured `provenance` object with append-only `attempts[]` (each carrying `qualification_status`, a real deterministic `calibration_class` from a new `derive_calibration_class()` per ADR-010's formula, outcome, and usage). `scores` is `dict[str, ScoreValue]` (`{value?, status, method_version, calibration_class}`); `groundedness`/`hallucination_risk`/`contradiction_risk` follow `scoring.md`'s exact claim-ratio formulas (no partial credit, `NOT_APPLICABLE` at a zero denominator); `citation_support`/`tool_correctness` are `NOT_APPLICABLE` rather than defaulted to `1.0` when nothing was supplied; `scope_breach`/`instruction_adherence`/`confidence_alignment` are always `UNAVAILABLE` because `scoring.md` defines no accepted v0.1 formula for them yet (the underlying violation detection for scope/instructions still runs and still produces violations). The prototype's weighted composite "reliability" score is deleted -- CONTRACTS.md has no such aggregate. A new `core.scoring.determine_verdict()` computes the factual `PASS|PARTIAL|FAIL|ABSTAIN` verdict from claim verdicts alone, independent of policy; `PolicyEngine` now only selects a policy action from that verdict plus threshold checks, and no longer upgrades the verdict itself from violation severity.

`ModelProvider` is renamed `JudgeProvider` and its required method is now `evaluate(JudgeRequest, deadline, cancellation) -> JudgeResult`, checking cancellation/deadline before dispatch and returning a typed `JudgeError` (`TIMEOUT|RATE_LIMIT|UNAVAILABLE|INVALID_RESPONSE|CANCELLED|CONFIGURATION`) rather than raising or fabricating a verdict. `extract_claims()` is removed from the provider interface entirely; claim segmentation is exclusively `core.claims`'s job. `Verifier`'s outer exception handler now only catches genuinely unexpected pipeline failures (not provider errors, which are handled per claim); on such a failure it returns `status=FAILED`, `verdict=ABSTAIN`, a typed `abstention_reason`, and a generic `metadata={"failure": "internal pipeline error"}` -- the real exception is logged via `logging`, never placed in the public result.

A follow-up fix the same day closes two response-validation gaps a second review found: `JudgeResult` now rejects (Pydantic validation error) any instance that sets both or neither of `verdict`/`error`, enforcing the port's own stated invariant instead of merely documenting it; and a provider is no longer trusted to self-police CONTRACTS.md's "`SUPPORTED` without a cited evidence ID is `INVALID_RESPONSE`" rule -- `judges.providers.validate_judge_result()` checks every judge response for this before `Verifier` uses it, downgrading a malformed `SUPPORTED` into `INVALID_RESPONSE` (which the existing per-claim error path turns into `INSUFFICIENT_EVIDENCE`, never `UNSUPPORTED`/`FAIL`). The deeper, contract-described "versioned, conservative non-model overlap/support check" on cited evidence content is not implemented -- only the presence-of-a-citation check is.

**What is still not closed, deliberately left open rather than guessed at.** Each item names the gate that owns it in [EXECUTION_PLAN.md](../EXECUTION_PLAN.md#reliability-prototypes-open-scope-against-these-gates) -- pick it up when that gate's own prerequisites are actually met, not before, since building it here first would mean redoing it against real gate infrastructure later:

- **Pre-dispatch caps, a real T0 adapter with usage reporting, and injection fixtures (pick up at G3).** There is no `MAX_CLAIMS_PER_REQUEST`-style cap, no evidence/token/cost ceiling check before dispatch, and no adversarial-evidence/prompt-injection fixture. `BUDGET_EXHAUSTED` should first appear here, scoped to a single request.
- **Qualification registry (pick up at G4).** `calibration_class` is genuinely derived (`derive_calibration_class()`), but `qualification_status` is hardcoded `UNQUALIFIED` on every attempt because there is no registry, conformance runner or tenant-approval step to say otherwise. Do not mark a provider `QUALIFIED` before G4's agreement report exists.
- **`DISPUTED` status and multi-judge reconciliation (pick up at G5).** One-claim-per-call with a single provider cannot structurally produce a dispute; this needs G5's bounded retries/fallback to ever have more than one valid attempt per claim to disagree. The type system can represent `DISPUTED` now (it must, to parse canonical fixtures); the pipeline still cannot produce it.
- **`NO_COMPLIANT_PROVIDER`/`REVOKED` abstention reasons and adapter trust tiers (pick up at G10).** These require the full registry lifecycle (`REGISTERED -> ... -> REVOKED`) and T1/T2 tiering G10 defines; there is nothing to revoke against or tier below T0 yet.
- **Authenticated tenant boundary (pick up at G3).** `TenantContext` (typed, with a real `authorizes()` check) exists now, but nothing calls it from a real boundary yet: `Verifier.verify(request, tenant_id=...)` is still a trusted Python argument, not an authenticated API boundary. There is no ingress authentication, no persistence to isolate, and no cross-tenant test against a real data store or forged-field attack -- G3's sync API is where `TenantContext` gets a real caller.

Do not mark REL-04/06/08 (or any REL task not named below) complete on the strength of this pass. It closes the specific wire-shape/provider-port/scoring gaps this document previously named, plus a follow-up response-validation fix (`JudgeResult` verdict-xor-error, `SUPPORTED`-without-evidence downgrade); it does not make the prototype contract-complete. The [migration notes](docs/PROTOTYPE_MIGRATION_NOTES.md) and [execution plan](../EXECUTION_PLAN.md) provide the next work order. (A fourth pass below moved REL-02/REL-03 to `IN_PROGRESS`, with the reasoning recorded there -- the blanket "stays `NOT_STARTED`" this paragraph originally stated no longer holds for those two.)

A second follow-up pass the same day closed a real gap a review found in the earlier response-validation fix: `validate_judge_result()` checked only that a `SUPPORTED` verdict cited *some* evidence ID, not that the ID actually belonged to the request -- a judge could cite a nonexistent evidence ID and have it accepted as valid support. `validate_judge_result()` now takes the `JudgeRequest` and rejects (as `INVALID_RESPONSE`) any cited evidence ID absent from the request's evidence, alongside the existing empty-citation check. Separately, `judges.providers.apply_citation_support_check()` now implements CONTRACTS.md's "versioned, conservative non-model overlap/support check" that G0/G3 previously left unimplemented: for a `SUPPORTED` verdict whose citations are all real (i.e. already past `validate_judge_result()`), it downgrades to `INSUFFICIENT_EVIDENCE` with a `CITATION_MISMATCH` violation only when the claim and every cited evidence text share zero non-trivial content words -- a deliberately weak check that catches a fabricated citation to unrelated real evidence without penalizing legitimate paraphrase (per CONTRACTS.md, "lexical overlap alone is never proof"). Both checks run per claim in `Verifier._verify_claims()`. This closes the specific "presence, not validity" gap; it is still the same conservative/weak check CONTRACTS.md describes, not a semantic entailment check -- a judge citing real evidence that happens to share one incidental word with the claim still passes.

A third pass the same day closed G0's contract-freeze deliverables: [`contracts/v0.1/`](../contracts/README.md) now has executable JSON Schemas and examples (including abstention/failure/dispute cases and fixtures the validator must reject), `CONTRACTS.md` settled the evidence/claim-result shape (plain `evidence_ids` arrays, a versioned `rationale_code` vocabulary) and the one-attempt-per-claim question (the worked example now shows two attempts for two claims, matching what this prototype already did). Building those fixtures surfaced two more naming gaps between this prototype and `CONTRACTS.md`, neither fixed in this pass: `schemas/verification.py`'s `Violation.claim_id`/`evidence_id` are singular optional strings, not the contract's `claim_ids`/`evidence_ids` plural arrays; and every `Violation.severity` in this codebase (`core/verifier.py`, `core/policy.py`) is lowercase (`"medium"`, `"critical"`, ...) where `CONTRACTS.md`'s worked example and enum convention are uppercase (`MEDIUM`, `CRITICAL`). Both are cheap renames, deliberately left for whoever picks up the G0 evidence/claim-verification field-rename item at G2, rather than fixed piecemeal here.

A fourth pass, on 2026-09-14, G2 work, adopted every canonical `contracts/v0.1` field name across `schemas/`, `judges/`, and `core/`: `Claim.id`→`claim_id`; `Evidence.id`/`extracted_text`→`evidence_id`/`content`+`reference` (a new `model_validator` enforces exactly one of the two, matching the contract's `oneOf`); `ClaimVerification` was rebuilt from evidence-reference objects with support/relevance scores into the contract's `ClaimResult` shape (`evidence_ids: list[str]`, `rationale_code`, `text_status`, `contributing_judgments[]`, a new validator requiring at least one `evidence_id` when `verdict=SUPPORTED`); `Violation.claim_id`/`evidence_id`→plural `claim_ids`/`evidence_ids` arrays with an uppercase `Severity` enum, and `message` became optional (a canonical fixture omits it, and the contract's schema never required it -- the model was stricter than the wire contract until this pass); `Citation`/`ToolExecution`/`Instruction` followed the same `*_id` renames and uppercase enum values. `VerificationResult` gained `dispute_reason`/`supersedes` and the full v0.1 status/verdict/abstention-reason vocabulary (`DISPUTED`, `BUDGET_EXHAUSTED`, `NO_COMPLIANT_PROVIDER`, `REVOKED`) so every valid canonical fixture parses, even though this pipeline cannot produce those values yet. `VerificationRequest` gained an unconsumed `claims` field for wire-compat and a `model_validator(mode="before")` that now *rejects* a client-supplied `tenant_id` outright instead of silently ignoring it (pydantic's default `extra="ignore"` behavior previously meant a spoofed `tenant_id` in the payload would just vanish, not fail loudly). `JudgeRequest`/`JudgeResult` (the judge-boundary port) followed: `evidence: list[EvidenceReference]`→`evidence_ids: list[str]`, plus a new `rationale_code` and unused-for-now `usage` field. `judges/providers.py`, `judges/vendor_adapters.py` (`EmbeddingProvider`/`NLIProvider`, re-verified against real downloaded models afterward) and `core/evidence.py`'s `SimpleEvidenceMapper` were rewritten to produce `evidence_ids`/`rationale_code` instead of scored evidence-reference objects. A new `tests/test_contract_fixtures.py` loads every canonical `contracts/v0.1` example (success/partial/fail/both abstention reasons/failed-internal-error/disputed, both request examples, judge request/result examples) through these types and asserts it parses, and asserts the relevant invalid fixtures are rejected by name -- CI now checks out `factlama-architecture` as a sibling to make this a real, own-CI compatibility run, not a claim resting on local-only execution. Separately, `schemas/tenancy.py`'s `TenantContext` (with a real `authorizes(project_id, application_id)` check, tested) and `core/repository.py`'s `TenantAwareRepository` `Protocol` give REL-02 a typed foundation; `Verifier.verify()`'s trusted `tenant_id: str` argument is deliberately left unchanged, since rewiring it to require `TenantContext` ahead of G3's API (the first real caller) would be premature plumbing. 179 tests pass (1 skipped) in a genuinely fresh venv with the base `[dev]` extras only; the 13 semantic-provider tests separately pass against real downloaded models.
