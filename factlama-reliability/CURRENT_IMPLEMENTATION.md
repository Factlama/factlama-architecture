# Reliability implementation snapshot

Checked locally on 2026-09-13. `schemas/`, `core/`, `judges/`, `tests/`, and `examples/` exist in the implementation repository. Running `.venv/bin/python -m pytest -q` produces **136 passed, 1 skipped**. This establishes that the migrated-and-revised prototype behaves as its own tests expect; it does not satisfy the accepted [cross-repository contract](../CONTRACTS.md) or close a REL task.

A follow-up pass this same day closed the specific gaps recorded below on 2026-09-13 (wire shape, JudgeProvider port, provenance/calibration, scoring formula). What follows describes the resulting state, not the original migration.

`VerificationRequest` no longer carries `tenant_id`: tenant identity is a trusted argument to `Verifier.verify(request, tenant_id=...)`, never a client-payload field. `question` is optional; the evidence field is named `evidence` (not `context`); `project_id`/`application_id` are required; `interaction_id`/`trace_id`/`span_id`/`model`/`prompt_version`/`policy_id` are accepted and, for `trace_id`/`span_id`, echoed rather than always regenerated. `VerificationResult` now carries `evaluation_id`, `status` (`COMPLETED|ABSTAINED|FAILED`), `abstention_reason` (`NO_CHECKABLE_CLAIMS|INSUFFICIENT_EVIDENCE|PROVIDER_FAILURE|CANCELLED`), and a structured `provenance` object with append-only `attempts[]` (each carrying `qualification_status`, a real deterministic `calibration_class` from a new `derive_calibration_class()` per ADR-010's formula, outcome, and usage). `scores` is `dict[str, ScoreValue]` (`{value?, status, method_version, calibration_class}`); `groundedness`/`hallucination_risk`/`contradiction_risk` follow `scoring.md`'s exact claim-ratio formulas (no partial credit, `NOT_APPLICABLE` at a zero denominator); `citation_support`/`tool_correctness` are `NOT_APPLICABLE` rather than defaulted to `1.0` when nothing was supplied; `scope_breach`/`instruction_adherence`/`confidence_alignment` are always `UNAVAILABLE` because `scoring.md` defines no accepted v0.1 formula for them yet (the underlying violation detection for scope/instructions still runs and still produces violations). The prototype's weighted composite "reliability" score is deleted -- CONTRACTS.md has no such aggregate. A new `core.scoring.determine_verdict()` computes the factual `PASS|PARTIAL|FAIL|ABSTAIN` verdict from claim verdicts alone, independent of policy; `PolicyEngine` now only selects a policy action from that verdict plus threshold checks, and no longer upgrades the verdict itself from violation severity.

`ModelProvider` is renamed `JudgeProvider` and its required method is now `evaluate(JudgeRequest, deadline, cancellation) -> JudgeResult`, checking cancellation/deadline before dispatch and returning a typed `JudgeError` (`TIMEOUT|RATE_LIMIT|UNAVAILABLE|INVALID_RESPONSE|CANCELLED|CONFIGURATION`) rather than raising or fabricating a verdict. `extract_claims()` is removed from the provider interface entirely; claim segmentation is exclusively `core.claims`'s job. `Verifier`'s outer exception handler now only catches genuinely unexpected pipeline failures (not provider errors, which are handled per claim); on such a failure it returns `status=FAILED`, `verdict=ABSTAIN`, a typed `abstention_reason`, and a generic `metadata={"failure": "internal pipeline error"}` -- the real exception is logged via `logging`, never placed in the public result.

A follow-up fix the same day closes two response-validation gaps a second review found: `JudgeResult` now rejects (Pydantic validation error) any instance that sets both or neither of `verdict`/`error`, enforcing the port's own stated invariant instead of merely documenting it; and a provider is no longer trusted to self-police CONTRACTS.md's "`SUPPORTED` without a cited evidence ID is `INVALID_RESPONSE`" rule -- `judges.providers.validate_judge_result()` checks every judge response for this before `Verifier` uses it, downgrading a malformed `SUPPORTED` into `INVALID_RESPONSE` (which the existing per-claim error path turns into `INSUFFICIENT_EVIDENCE`, never `UNSUPPORTED`/`FAIL`). The deeper, contract-described "versioned, conservative non-model overlap/support check" on cited evidence content is not implemented -- only the presence-of-a-citation check is.

**What is still not closed, deliberately left open rather than guessed at.** Each item names the gate that owns it in [EXECUTION_PLAN.md](../EXECUTION_PLAN.md#reliability-prototypes-open-scope-against-these-gates) -- pick it up when that gate's own prerequisites are actually met, not before, since building it here first would mean redoing it against real gate infrastructure later:

- **Evidence/claim-verification field renames (pick up at G0, then G2).** `Evidence.id`/`extracted_text` are still not CONTRACTS.md's `evidence_id`/`content`+`reference`; `ClaimVerification.evidence` is still evidence-reference objects with support/relevance scores, not a plain `evidence_ids` list plus a separate `contributing_judgments[]`/`text_status`/`rationale_code`. These are canonical v0.1 types G0 already commits to defining; implement them here only once G0's canonical fixtures fix their shape, via G2's typed request/result models -- not as a local guess now.
- **Attempts-per-claim vs. the CONTRACTS.md worked example (resolve at G0).** The `JudgeProvider.evaluate()` port takes exactly one claim, so this implementation records one `Attempt` per claim. CONTRACTS.md's worked example shows a single attempt covering two claims. This is a real, unresolved tension between the port signature and the illustrative fixture; G0's contract-freeze work should settle it explicitly rather than leave two documents disagreeing.
- **Pre-dispatch caps, a real T0 adapter with usage reporting, and injection fixtures (pick up at G3).** There is no `MAX_CLAIMS_PER_REQUEST`-style cap, no evidence/token/cost ceiling check before dispatch, and no adversarial-evidence/prompt-injection fixture. `BUDGET_EXHAUSTED` should first appear here, scoped to a single request.
- **Qualification registry (pick up at G4).** `calibration_class` is genuinely derived (`derive_calibration_class()`), but `qualification_status` is hardcoded `UNQUALIFIED` on every attempt because there is no registry, conformance runner or tenant-approval step to say otherwise. Do not mark a provider `QUALIFIED` before G4's agreement report exists.
- **`DISPUTED` status and multi-judge reconciliation (pick up at G5).** One-claim-per-call with a single provider cannot structurally produce a dispute; this needs G5's bounded retries/fallback to ever have more than one valid attempt per claim to disagree.
- **`NO_COMPLIANT_PROVIDER`/`REVOKED` abstention reasons and adapter trust tiers (pick up at G10).** These require the full registry lifecycle (`REGISTERED -> ... -> REVOKED`) and T1/T2 tiering G10 defines; there is nothing to revoke against or tier below T0 yet.
- **Authenticated tenant boundary (pick up at G2).** `tenant_id` is correctly kept out of the request payload, but `Verifier.verify(request, tenant_id=...)` is a trusted Python argument, not an authenticated API boundary -- there is no ingress authentication, no persistence to isolate, and no cross-tenant test against a real data store or forged-field attack.
- **No golden/contract fixture suite against this repository's canonical JSON examples (blocks on G0).** The 142 passing tests are this repository's own unit/golden tests, not a compatibility run against `factlama-architecture`'s fixtures (G0's exit evidence). Nothing downstream should claim compatibility until G0 actually publishes those fixtures.

Do not mark REL-02/03/04/06/08 (or any REL task) complete on the strength of this pass. It closes the specific wire-shape/provider-port/scoring gaps this document previously named, plus a follow-up response-validation fix (`JudgeResult` verdict-xor-error, `SUPPORTED`-without-evidence downgrade); it does not make the prototype contract-complete. The [migration notes](docs/PROTOTYPE_MIGRATION_NOTES.md) and [execution plan](../EXECUTION_PLAN.md) provide the next work order. All REL task statuses remain `NOT_STARTED` until those gates pass.
