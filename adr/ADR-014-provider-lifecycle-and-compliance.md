# ADR-014: Provider Lifecycle, Pinning, and Compliance Constraints

Status: Accepted

Decision: The evaluator registry is specified as a first-class control-plane component with an explicit lifecycle: `REGISTERED -> CONFORMANCE_PASSED -> AGREEMENT_REPORTED -> TENANT_APPROVED -> {DEPRECATED, REVOKED}`. Conformance (the existing success/ambiguity/timeout/rate-limit/malformed-response fixture suite) runs as a gate, not only a CI test; configuring a provider and approving it for default routing are separated duties; `REVOKED` propagates immediately to in-flight evaluations and to any policy naming the provider as a fallback; each transition is audited. A registered provider's model identifier must be pinned and non-aliased — a floating alias is not permitted for a tenant's default judge — and any provider-side model change is treated as a new calibration class (ADR-010), detected by a periodic canary that re-runs the golden set against each approved provider and alerts on agreement drift. Registry entries carry compliance attributes (`hosting_region`, `data_processing_terms_ref`, `trains_on_submitted_data`, `retention_at_provider`, `subprocessors`, `certifications[]`); tenant policy expresses constraints over these attributes, not only an allowlist, and fallback selection must satisfy the same constraints as primary selection. When no compliant provider is available, the result is `ABSTAIN` plus `HUMAN_REVIEW`, never a silent non-compliant call — consistent with the existing fail-closed rule for redaction failures. Historical results are never mutated in place; re-scoring against a changed provider or configuration creates a new `evaluation_id` with a `supersedes` link, and dashboards annotate calibration-class changes on trend lines.

Rationale: `judge-provider.md` references "the registry" and EPIC-07 lists it as a checkbox, but no document specifies it, despite it being the most important control-plane object once judges are pluggable. Immutable "configuration version" does not protect against a floating model alias changing behavior underneath a fixed configuration. Residency and compliance are documented today only for storage (`PRIVACY.md`, `SECURITY.md`, EPIC-14), but for a tenant running FactLama's own recommended metadata-only default, the judge call — which transmits `evidence[].content` across an organizational and geographic boundary — is the actual compliance-relevant event, not persistence. Re-scoring semantics exist for the deferred Interaction Store (ADR-008) but are silently unavailable under metadata-only capture, which is the default; that consequence should be stated, not discovered.

Consequences: New `factlama-reliability/docs/evaluator-registry.md`. EPIC-07's "provider registry" and "second/custom provider path" are gated on this ADR and on ADR-011 before opening to customer-supplied judges. `PRIVACY.md`/`INTERACTION_STORE.md` state the metadata-only-excludes-cross-version-re-scoring tradeoff explicitly. Judge-egress residency constraints move earlier in the roadmap than storage residency (EPIC-14), since they bind at EPIC-07 rather than at enterprise hardening.
