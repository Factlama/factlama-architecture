# ADR-012: Verification Budgets and Cost Ownership

Status: Accepted; enforcement delivery scope amended by [ADR-017](ADR-017-mvp-unmetered-evaluators.md).

Delivery scope (2026-09-18): MVP uses local, unmetered evaluators. Hard token/cost ceilings are a post-MVP prerequisite for enabling the first metered adapter; claim/evidence and execution limits remain MVP requirements. The decision below describes the target metered capability.

Decision: Verification enforces a first-class budget: per-request and per-tenant-per-window token and cost ceilings, checked before dispatch and decremented across retries and fallback attempts, plus a hard `MAX_CLAIMS_PER_REQUEST` and `MAX_EVIDENCE_PER_CLAIM`. Exceeding a budget produces `ABSTAINED`/`ABSTAIN` with a new typed reason, `BUDGET_EXHAUSTED` — consistent with the existing rule that a technical failure yields abstention, never a factual verdict — and emits an alertable metric. Judge usage (tokens, cost, latency) returned by `JudgeResult` is plumbed through `provenance` into `ReliabilityEvent` and stored, so verification cost is queryable per tenant, per provider, and per mode. Bring-your-own-key is the default and only economic model: the tenant's credential is used to call the tenant's approved provider, billed directly by that provider to the tenant; FactLama does not broker or mark up model calls.

Rationale: Nothing in the current design bounds tokens or money on the judge path, while claim segmentation is server-side and answer-length-driven (`claim-engine.md`) — so judge calls scale roughly as `claims_extracted × evidence_volume × (1 + retries) × (1 + fallback_attempts)`, a fan-out an attacker-influenced request can amplify, and fallback-on-failure doubles spend precisely during a provider brownout. Separately, README.md's product thesis — "FactLama does not sell another model call; it aims to reduce the number of expensive calls required" — is currently unmeasurable in FactLama's own dashboard, since judge usage has a producer (`JudgeResult`) and no consumer. BYO-key makes the thesis literally true, keeps denial-of-wallet liability with the party controlling the spend, and avoids building a billing subsystem the product does not need.

Consequences: `CONTRACTS.md` gains a `BUDGET_EXHAUSTED` error/provider-error type and `attempts[].usage` on provenance, feeding `reliability_events` usage columns and a dashboard cost view (verification cost per evaluation, verification-to-generation cost ratio) reusing the existing pricing discipline (versioned price table, unknown price is `UNAVAILABLE` not zero, never sum currencies). `PRODUCT_BOUNDARIES.md` states BYO-key as the default explicitly. A future hosted/brokered tier is a deliberate reversal requiring its own ADR and abuse model, not a default that drifts in.
