# Architecture validation and MVP gates

Documentation establishes target behavior; all implementation status remains `NOT_STARTED`. The first cross-repository fixture is the [worked example](CONTRACTS.md#worked-example). Both implementations must serialize/deserialize it under schema v0.1 and preserve tenant and correlation IDs. Negative fixtures must cover unknown schema major, duplicate claim/evidence IDs, cross-tenant identifiers, missing evidence, conflicting evidence, provider timeout, duplicate async delivery, duplicate Reliability event, and metadata-only capture.

MVP acceptance requires a fresh checkout of implementation repositories to start the documented Compose stack, run migrations and seed a sample tenant, instrument an LLM/RAG request, ingest/query its trace, submit an evidence-backed verification, inspect claim findings and provenance, correlate the evaluation in the dashboard, and pass contract, failure, isolation and content-suppression tests. A smoke test must assert the same `interaction_id`, `trace_id` and `evaluation_id` across API result, event and query projection. Performance baselines should report machine/configuration, ingestion throughput, evaluator latency, query latency and resource use; no arbitrary enterprise scale claim is implied.

Changes to shared fields or verdict semantics require a compatibility fixture, ADR and a coordinated release plan. CI in each repo should run its local fixtures; an integration workflow should test compatible released revisions of all three repositories. A passing document link/JSON check is useful but does not satisfy runtime acceptance.
