# Cross-repository execution plan

This is the **build order and integration gate** for the three initial repositories. It is a target plan, not an assertion that code exists. [ROADMAP.md](ROADMAP.md) owns EPIC status; the centralized [Reliability](factlama-reliability/docs/implementation.md) and [Observability](factlama-observability/docs/implementation.md) task ledgers own REL/OBS status. All implementation statuses remain `NOT_STARTED` until their own acceptance tests pass. [CONTRACTS.md](CONTRACTS.md) and ADR-001–016 are the architecture baseline. Implement a thin, tested vertical slice at each gate; avoid creating every future module up front.

ADR acceptance and the document contract are complete. Executable canonical fixtures and a standalone schema/compatibility validator now exist at [`contracts/v0.1/`](contracts/README.md), covering `VerificationRequest`/`VerificationResult`/`JudgeRequest`/`JudgeResult`/`ReliabilityEvent` including abstention, failure and dispute cases, plus fixtures the validator must reject (unknown major version, forged `tenant_id`, missing required field, `SUPPORTED` without valid evidence). Two previously-open contract details are settled there and in `CONTRACTS.md`: the evidence/claim-result shape (plain `evidence_ids` arrays, never scored evidence-reference objects, plus a versioned `rationale_code` vocabulary) and one judge attempt per claim (the worked example now shows two attempts for two claims). G0 is a documentation gate — the validator does not depend on either implementation repo's own test/CI foundation, since that foundation is G1's deliverable; running this same fixture set inside each repo's own test framework is G2's exit evidence, not G0's. **G0 is closed**: Reliability's `domain-model.md`, `judge-provider.md`, `verification-pipeline.md` and `LOW_LEVEL_IMPLEMENTATION.md`, and Observability's `telemetry-model.md` and `LOW_LEVEL_IMPLEMENTATION.md`, have been reconciled to the settled shapes; `scoring.md`/`storage-query.md`/`dashboard.md` were reviewed and needed no change. `evaluator-agreement-harness.md` and `evaluator-registry.md` were originally listed as G0 deliverables in the paragraph below, but their actual subject matter — a conformance/agreement runner and a registry state machine — is G4's own work product, not a contract-freeze artifact; carrying their creation forward as a G0 blocker was a sequencing error in this plan, corrected here. They are now written as G4 documents (see the G4 row and the gate-mapping note below); G0 does not depend on them.

The centralized low-level checklists predate ADR-010–015. G0 includes updating Reliability's `domain-model.md`, `judge-provider.md`, `scoring.md`, `verification-pipeline.md`, `LOW_LEVEL_IMPLEMENTATION.md`, plus new `evaluator-agreement-harness.md` and `evaluator-registry.md`; Observability must update `telemetry-model.md`, `storage-query.md`, `dashboard.md` and `LOW_LEVEL_IMPLEMENTATION.md`. Those documentation edits belong in the component folders in this architecture repo and are prerequisites for coding against this version of the shared contract.

## Dependency graph

```text
G0 architecture contract/fixture freeze (documentation gate)
  -> G1 repository/CI foundation
  -> G2 trusted tenancy + executable contracts
       ├─> G3 first T0 groundedness slice -> G4 evaluator agreement/qualification -> G5 async/content hardening
       └─> G6 observability ingress/store/query foundation ------------------------┘
                                                        G5 + G6 -> G7 SDK/correlation
                                                        G6 + G7 -> G8 dashboard
                                                   G4 + G5 + G7 + G8 -> G9 local MVP
                                                   G4 + G5 -> G10 evaluator ecosystem (post-MVP)
```

The observability lane may progress in parallel with Reliability after G2. G7 cannot be closed until a real Reliability result is linked to a persisted trace. G8 can start with fixtures but cannot close on mocked data alone. G10 is a deliberate ecosystem gate, not a prerequisite for the one-T0-judge MVP. `G9` is the only MVP completion gate.

## Reliability prototype's open scope against these gates

The `factlama-reliability` prototype (schemas/core/judges/api, see [CURRENT_IMPLEMENTATION.md](factlama-reliability/CURRENT_IMPLEMENTATION.md)) has closed several G0/G2/G3-flavored gaps ahead of G1 actually starting: typed request/result wire shapes, a bounded `JudgeProvider` port with response validation, and v0.1 claim-ratio scoring. It is no longer only a library: G3's `api/` package gave it a real authenticated synchronous HTTP service (`POST /v0.1/verifications`, smoke-tested against a running `uvicorn` process), even though the async/job surface (G5) does not exist yet. Several remaining items are real gate dependencies, not oversights -- pulling them forward would mean redoing them once the owning gate's infrastructure exists. This maps each open item to the gate that owns it; it does not restate REL task status, which stays solely in the [Reliability task ledger](factlama-reliability/docs/implementation.md).

- **G0 (contract freeze).** Closed. `evidence_id`/`content`+`reference`, `ClaimVerification.evidence_ids`, `contributing_judgments[]`, `text_status`, and `rationale_code` were defined once in [`contracts/v0.1/`](contracts/README.md)'s canonical JSON fixtures and schemas, plus a versioned `rationale_code` vocabulary in `CONTRACTS.md`; `factlama-reliability` has now adopted every one of these shapes (G2 work, see below), verified by running `contracts/v0.1`'s own canonical fixtures through its types in its own CI.
- **G2 (trusted tenancy + executable contracts).** Closed for Reliability's own scope. Typed request/result models match `contracts/v0.1` exactly, `TenantContext.authorizes(project_id, application_id)` exists and is tested, and it now has a real caller: `factlama-reliability/api/app.py`'s synchronous `POST /v0.1/verifications` authenticates a request to a `TenantContext` and calls `.authorizes()` before the request reaches `Verifier.verify()`. A genuine forged-tenant-field/cross-tenant test now runs against that live boundary (`tests/test_api.py`), not just typed-context logic against a Python argument. The persistence half of "cross-tenant IDs/jobs/cursors...fail safely" still needs G5, which does not exist.
- **G3 (first factual vertical slice).** Closed for Reliability's own scope. Closed across the 2026-09-15/16 and 2026-09-18 passes: pre-dispatch claim/evidence caps and provisional post-call usage checks (`core/budgets.py`, `MAX_CLAIMS_PER_REQUEST`/`MAX_EVIDENCE_PER_CLAIM`/`check_usage_budget`, `BUDGET_EXHAUSTED` scoped to one request); a baseline `NO_COMPLIANT_PROVIDER` check (`core/compliance.py`, a static tag comparison against `Policy.required_provider_compliance`, not a lookup against G4's registry); an evidence-injection defense-in-depth signal with a dedicated `HUMAN_REVIEW` policy-routing rule (`judges/port.py`'s `detect_evidence_injection()` plus `core/policy.py`'s forced routing, ADR-013); explicit-claims consumption (`VerificationRequest.claims`, previously typed but unused); claim-ID stability and source-offset preservation (`core/claims.py`'s `extractor_id`/`extractor_version` and `Claim.start_char`/`end_char` population, REL-04); a checked-in runnable API example (`examples/api_usage.py`, REL-12); and the synchronous API itself. The pre-existing T0 in-process adapters (`EmbeddingProvider`/`NLIProvider`, real downloaded models, no vendor API key) already satisfied "one T0 working judge adapter" before this pass -- see `factlama-reliability/docs/implementation.md`'s REL-06 entry. This summary does not establish a hard spending guarantee or waive accounting correctness findings; hard per-request and tenant-window token/cost ceilings are deferred to the post-MVP metered-enablement prerequisite in ADR-017, and REL-05/REL-09's own non-G3-blocking follow-ups (an unwired `EvidenceRetriever`, policy decision-provenance) are tracked in the Reliability ledger, not here.
- **G4 (first evaluator qualification).** First slice started 2026-09-18, not complete. `qualification_status`/`calibration_class` are still computed locally at dispatch (`derive_calibration_class()`) with every attempt hardcoded `UNQUALIFIED` -- that is unchanged, deliberately: the new registry state machine (`factlama-reliability/core/qualification.py`, per [`evaluator-registry.md`](factlama-reliability/docs/evaluator-registry.md)) and agreement-report runner (`scripts/run_agreement_harness.py`, per [`evaluator-agreement-harness.md`](factlama-reliability/docs/evaluator-agreement-harness.md)) exist and are tested, but nothing wires either into `Verifier`'s dispatch path yet, and the runner's fixture set is 6 illustrative dev items, not the hand-reviewed dev+held-out datasets the spec requires. Do not mark a provider `QUALIFIED` before a real report exists -- `core/qualification.py`'s state machine structurally cannot reach `AGREEMENT_REPORTED` without one. This gate is also where a minimal registry entry first exists, which G5 needs to carry a revoked flag -- the `QualificationRecord` type exists now; G5 is what gives it a caller and persistence.
- **G5 (durable Reliability).** `DISPUTED` status and cross-attempt disagreement reconciliation depend on this gate's bounded retries/fallback producing more than one valid attempt per claim; the current one-claim-per-call MVP structurally cannot dispute. G5 retains bounded retries, deadlines and durable attempt usage. Hard tenant-window monetary/token reservation enforcement moves to post-MVP under ADR-017. This gate's own deliverables also name "revocation checks": a baseline `REVOKED` abstention reason belongs here too, checked against G4's minimal registry entry before dispatch and before result commit -- not the full `REGISTERED -> ... -> REVOKED` audited lifecycle, which is G10's.
- **G10 (open evaluator ecosystem).** Baseline `NO_COMPLIANT_PROVIDER` (G3) and `REVOKED` (G5) abstention behavior already exists by MVP; this gate extends both to T1/T2 adapter tiers, full registry lifecycle/audit trail, and compliance-constrained primary/fallback selection across trust tiers. Do not implement T1/T2 dispatch or cross-tier fallback before G4's registry and G5's baseline revocation check exist to extend.

**First coding task:** G1's smallest foundation slice, followed immediately by G2's shared request/result/event fixture and tenant boundary. Do not begin SLM training, dashboard charts or a T2 extension point as the first implementation. Within G3, start with explicit claims and supplied evidence; add extraction once the direct path passes. The first production-like demonstration is the G3 sync API result, then the G7 trace correlation, then the G9 local stack.

## Cross-repository handoffs

| Producer → consumer | Contract and owning test | Failure behavior |
|---|---|---|
| Reliability API/worker → SDK client | `VerificationRequest/Result`, jobs, error shape; shared fixture in both repos | SDK distinguishes factual abstention, dispute and transport error |
| Reliability outbox → Observability ingress | `ReliabilityEvent` with stable event ID, calibration class and usage; at-least-once integration test | Delivery retries; duplicate does not double-count; trace remains visible if event delayed |
| SDK → Collector | W3C context and OTLP/HTTP spans; metadata-only fixture | Export is bounded/fail-open for customer inference; collector rejects bad auth/limits |
| Collector → Query API | Tenant-keyed spans/events/link projection and pricing provenance | Missing evaluation/cost is pending/unavailable, never PASS/zero |
| Query API → Dashboard | Versioned list/detail/aggregate envelopes and delegated sanitized Reliability detail | Empty, delayed, unavailable, denied and failed states are rendered separately |

Every handoff needs a producer fixture, a consumer contract test and one cross-repo integration test against compatible revisions. The architecture repo owns the fixture schema and compatibility policy; implementation repos own executable tests. A change to verdict, event, score or tenant semantics requires an ADR and coordinated release.

## Qualification and registry gates

The **first T0 adapter** may be used in development while `PROVISIONAL`, but cannot be selected as a tenant's default judge until G4 publishes its agreement report, assigns `QUALIFIED`, pins its model/configuration and records tenant approval. The report must state dataset versions, held-out isolation, per-class confusion matrix/precision/recall/F1, calibration if a probability is claimed, adversarial-evidence outcomes, latency, tokens and cost. A class-specific score is not pooled with another class. The harness is a runner/report, not a human certification bureaucracy; a tenant may explicitly choose an unqualified judge for nondefault use with that status visible.

The **customer-judge gate** is G10. T2 customer adapters are HTTP-only and out of process. Registry transitions are audited: `REGISTERED -> CONFORMANCE_PASSED -> AGREEMENT_REPORTED -> TENANT_APPROVED -> DEPRECATED|REVOKED`. Selection checks tenant approval, pinned model, qualification for default use, hosting/data-processing constraints, budget and breaker state on both primary and fallback. Revocation blocks new dispatch immediately and is rechecked before result commit; cancellation of an already-running external call is best effort and recorded. A compliant provider absence yields `ABSTAINED/ABSTAIN` plus `HUMAN_REVIEW`.

## Explicitly deferred after MVP

EPIC-12's FactLama SLM uses G4's provider-neutral harness and must pass the same qualification gate. EPIC-13 Interaction Store/replay enables cross-version re-evaluation only for tenants that opted into sufficient content retention. EPIC-14 covers enterprise SSO/Kubernetes/storage residency; judge-egress compliance is already enforced at G10. Multi-judge ensembles, majority voting and automatic reconciliation stay deferred under ADR-015; the contract can represent attempts and `DISPUTED` without implementing ensembles. Mode profiles permit one judgment per claim in MVP; a later ADR must define ensemble behavior. All these tasks remain `NOT_STARTED` until separately implemented and tested.

## MVP budget boundary (ADR-017)

[ADR-017](adr/ADR-017-mvp-unmetered-evaluators.md) supersedes earlier budget delivery timing. G3–G9 support local, unmetered evaluators only. Fixed reservations are estimates, not hard spending guarantees. REL-13/EPIC-07 owns the post-MVP implementation and acceptance tests for enforceable caps, atomic reservations, usage reconciliation and tenant-window accounting. No metered adapter may be enabled before these pass, even if introduced outside G10. Accounting correctness remains required now.
