# MVP identity, tenancy and content controls

The MVP may use one locally configured API-key issuer, but its trust semantics must match enterprise identity: a validated credential resolves an immutable tenant ID, actor/workload ID, allowed projects/applications and scopes. Scopes distinguish telemetry write, verification submit/read, query read and administrative configuration. Services never accept tenant ID from an unauthenticated header or body. Internal calls use workload identity or a signed tenant context with expiry and audience; worker messages carry the same scope. Revocation and key rotation must be supported by the configuration boundary.

All persistence keys and query predicates include tenant ID, backed by database constraints or row-level security where available. Cached objects and idempotency keys include tenant ID. Cross-tenant unknown and forbidden resource IDs return indistinguishable 404 responses. Control-plane changes (credentials, policies, provider references, capture/retention settings) produce an audit record with actor, tenant, prior/new version and timestamp; audit records exclude secrets and raw content.

MVP defaults to metadata-only content capture. `NONE` suppresses optional interaction metadata beyond operational necessities; `METADATA_ONLY` stores allowed identifiers/measurements and result metadata; `REDACTED` persists only selected content after redaction; `FULL` requires explicit tenant opt-in. Operational logs and queues obey the same rule. Redaction failures fail closed for content persistence but can still emit sanitized operational failure metrics. Credentials never enter judge requests, telemetry or audit payloads. Encryption in transit and at rest is required for deployment; local development may use documented nonproduction credentials.

Threat tests must cover forged tenant fields, cross-tenant IDs/cursors/jobs/cache, stale worker context, replayed events, privilege escalation, redaction bypass via errors/logs, oversized payloads and secret leakage to model providers. External provider egress is tenant-approved and recorded with provider/config version.

## Judge boundary and adapter tiers

Evidence and tool outputs are adversarial data at the judge boundary. Versioned prompt templates structurally separate instructions from evidence; one claim per judge call is a security boundary and cannot be widened without an ADR. Deterministic validation rejects `SUPPORTED` without cited evidence, and a suspected injection is recorded and routed to human review rather than silently dropping evidence. This reduces blast radius and improves detection; it does not guarantee prompt-injection prevention. Free-text judge rationale is rendered as inert text, without active HTML/Markdown links or images.

T0 first-party code may run in process. T1 partner code requires signature, version pin, code review, conformance and agreement report before installation. T2 customer adapters run out of process over versioned HTTP with mTLS, host allowlist, bounded payload/deadline and no DB/queue access. Credential resolution is per `(tenant_id,provider_id)` and per call; no adapter gets a general secrets API. Every dispatch checks tenant approval, hosting/data-processing constraints, pinned model, budget and breaker state, including fallback. No compliant provider means abstention plus human review.

Extend threat tests to cover evidence-borne prompt injection, SSRF via provider URLs, T1 supply-chain compromise, T2 secret over-scoping, denied-wallet fan-out, unsafe rationale rendering, provider revocation races, floating-model drift and slow-provider cross-tenant head-of-line blocking. Per-tenant/provider/model concurrency caps and circuit breakers isolate slow judges.
